# Original libnx framebuffer presentation

Follow-up: [one, two and three buffers](LIBNX_FRAMEBUFFER_BUFFERS.md) adds local fair reuse. The same original binaries now execute 152895 instructions (16x16) and 378310 (37x137); measurements below describe their earlier reuse policy.

Follow-up: [padded and multiple-block geometry](LIBNX_FRAMEBUFFER_GEOMETRY.md) adds a separate 37x137 reference and generalizes the bounded geometry. The 16x16 measurements below remain unchanged.

This separate project harness calls unchanged pinned libnx framebufferCreate,
framebufferMakeLinear, framebufferBegin, framebufferEnd and framebufferClose.
It draws two 16x16 RGBA patterns in the linear buffer. Original framebuffer.c
converts each to block-linear storage, original arm/cache.s flushes the range,
and the original native-window/producer client queues it. No SDK function body
or serializer is replaced. The harness retains the explicit 64 KiB NV
communication-memory override of the small-heap reference profile.

The emulator accepts the already validated bounded descriptor: a 16x16 RGBA
surface, pitch 64 bytes, block-height log2 4, layout 3, kind 0xfe and 8192-byte
extent. The two surfaces share a 16384-byte Nvmap object at offsets 0 and 8192.
Queue validates the chosen extent and its readability, converts its visible
pixels to an immutable RGB snapshot, then publishes it and releases ownership
only after IPC/parcel replies are written successfully. Alpha is discarded.
There is no GPU execution, hardware fence, vsync or asynchronous GPU consumer.

## Conversion and independent oracle

Each GOB contains 64 bytes by eight rows, ordered in 16-byte by two-row sectors.
For this one-block-wide profile, the visible byte address is:

```
(y / 8) * 512 + (byte_x / 32) * 256 + ((y % 8) / 2) * 64
+ ((byte_x % 32) / 16) * 32 + (y % 2) * 16 + byte_x % 16
```

The implementation reads from the retained surface offset, not the slot index.
The test draws R=x*17, G=y*17, B=(x^y)*17, then their complements. It verifies
all RGB pixels of both published frames against those original linear colors.
The GOB data is generated by unchanged SDK software conversion, independently
of the emulator's address formula. Each snapshot remains valid after later
writes and original backing cleanup. Normal and seven-instruction execution
slices follow the same original path in 150676 instructions, producing two frames.

A separate host replay holds slot zero, acquires slot one, fills only its
8192-byte extent with 42 and queues it. Every resulting pixel must be 42.
This extra host-driven replay is separate from the two original guest frames.
Malformed crop, unreadable backing, protected IPC reply and duplicate Queue
cases verify failure handling without premature frame/ownership publication.
The inherited registration tests check descriptor preservation and rollback.

## Local cache maintenance

The original flush routine requires MRS CTR_EL0 and DC CIVAC. The interpreter
now exposes an explicit local geometry: 64-byte I/D lines, a 16-byte exclusive
reservation granule, a 64-byte writeback granule and a PIPT instruction policy.
This is not a Switch 2 hardware-register value. RAM has no separate simulated
cache and no translated instruction cache. DC CIVAC therefore validates the
complete addressed 64-byte RAM line without writing memory or changing flags.
Unaligned addresses are accepted; inaccessible RAM, MMIO and out-of-range
addresses fail explicitly. Privilege traps and VA-to-PA translation remain
unimplemented. DC ZVA and other unimplemented cache operations still fail.

Architecture references: [Arm CTR_EL0 field descriptions](https://documentation-service.arm.com/static/6040c321ee937942ba301626)
and [Arm DC CIVAC](https://support.arm.com/documentation/ddi0601/2026-09/AArch64-Instructions/DC-CIVAC--Data-or-unified-Cache-line-Clean-and-Invalidate-by-VA-to-PoC?lang=en).
These establish field/operation meanings; the geometry and RAM-only policy are
local emulator choices. A dedicated CPU suite checks geometry, unaligned and
read-only RAM, invalid addresses, state preservation and unsupported zeroing.

## Reproduction and scope

Rebuild the guest with tools/build_libnx_framebuffer_present.ps1 using the
pinned toolchain. Source hashes and NRO provenance are recorded in
../tests/programs/libnx_framebuffer_present/reference.json. Existing reference
binaries are unchanged. Rebuild host targets before running CTest. Debug and
Release CTest runs must be sequential because some test outputs are shared.

The new host test optionally exports the final snapshot as PNG:

```powershell
.\build\Debug\libnx_framebuffer_tests.exe .\tests\programs\libnx_framebuffer_present\program.nro .\tests\programs\libnx_framebuffer_present\symbols.txt --present .\build\original-framebuffer.png
```

This advances the original Switch libnx software-framebuffer path. General
surface formats/dimensions, GPU commands/shaders, native Switch 2 compatibility
and commercial-game execution remain unvalidated.
